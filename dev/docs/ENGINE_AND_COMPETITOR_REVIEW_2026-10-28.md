## 1. Главное

1. **Инженерные практики у undatum сильные, слабое место — исполнение.** В проекте есть OpenSpec-процесс, версионированные JSON-ответы, документированные коды выхода, mypy-ratchet, бюджеты памяти в CI и 22 тыс. строк тестов. Но скорость и корректность упираются в построчный Python-путь и в неполное использование DuckDB.
2. **Где undatum уже передаёт работу DuckDB, он в 2–17 раз медленнее «голого» DuckDB CLI** на 2 млн строк. Причины: фиксированные накладные расходы (~0,6 с только на импорт iterabledata, pyarrow и duckdb), возврат результатов через `fetchall` в Python-словари, `threads=1`. Где не передаёт (`convert` CSV→JSONL, `dedup`), отставание 12–43 раза.
3. **Три дефекта важнее любого выбора движка:**
   - `stats` тратит около 100 с на файл любого размера, если в нём есть текстовые столбцы с цифрами (хэши, адреса, описания). Детектор дат qddate тратит 33–55 мс на такое значение, а `TypeGuesser` проверяет до 1000 значений на поле.
   - DuckDB-путь читает CSV с `ignore_errors=true` и без кодировки. В результате `undatum head` на CSV в cp1251 выводит 0 строк и завершается с кодом 0 — тихая потеря данных. При этом `undatum sniff` распознаёт кодировку правильно.
   - Python-реализация `uniq` квадратична (`if k not in uniqval` по списку): на 200 тыс. строк она работает 99 с.
4. **Polars как основной движок не рекомендуется.**
   - По скорости он на уровне DuckDB: в наших замерах быстрее только на сортировке.
   - Бинарный runtime занимает 153 МБ против 44 МБ у DuckDB.
   - Строже к «грязным» CSV: падает на смене типа после 100-й строки и на cp1251.
   - Мажорная версия выходит раз в ~6 месяцев (2.0 — октябрь 2026).
   - Дублирует SQL-слой, который в undatum уже построен на DuckDB.

   Polars стоит оставить как опцию SDK с обменом данными через Arrow.
5. **Рекомендация — «DuckDB-first, Arrow-native»:**
   - DuckDB становится единым движком для всех операций над множествами записей.
   - Arrow служит мостом к iterabledata для 140+ форматов.
   - Построчный Python остаётся только там, где у операции нет SQL-формы.

   Одновременно нужен переход на Python ≥3.11 и DuckDB 2.0 LTS. DuckDB 2.0 вышел 21.10.2026 и требует Python ≥3.11. Python 3.10 — EOL в октябре 2026, ветка DuckDB 1.5 — EOL 01.03.2027.
6. **Конкуренты.**
   - Ближайший конкурент — qsv (Rust): MCP-сервер, `describegpt`, CKAN, коммерческий qsv pro.
   - По чистой скорости на CSV выигрывают qsv и xan.
   - DuckDB CLI — стандарт для SQL по файлам, Miller — эталон UX и документации, csvkit — главный источник пользователей для миграции.
   - Поле качества данных занимают frictionless-py, Soda Core, GX и datacontract-cli.

   Ниша, которую undatum может занять: широта форматов, валидация, качество, дрейф схем и Frictionless, безопасные инструменты для агентов и Python SDK — всё в одной MIT-установке. Соревноваться с Rust-инструментами в сырой скорости разбора CSV не нужно.

## 3. Как устроено исполнение

### 3.1 Выбор движка

`detect_engine()` (`undatum/common/engine_selector.py:48-88`) выбирает DuckDB только при одновременном выполнении трёх условий:

- формат — csv, jsonl, json или parquet;
- сжатие — нет, gz или zst;
- операция есть в списке SQL-выразимых.

`convert` в этот список не входит. Второй фильтр — `force_iterable_if_table` (`command_utils.py:273`): он принудительно включает Python при `--table`/`--sheet`, `--on-error skip|warn`, `--error-log`, `--quotechar` и `--flatten-nested`. Собственные списки «DuckDB-совместимых» форматов есть ещё в `io/source.py:67-94` и `ingester/base.py:3-5`.

### 3.2 Путь исполнения по командам

| Команда | DuckDB | Python (iterabledata) | Замечания |
|---|---|---|---|
| convert | Только при `--engine duckdb`, `--low-memory` или выводе в Parquet; партиции через `COPY ... PARTITION_BY` | По умолчанию, в том числе CSV→JSONL | Отставание от DuckDB — 12 раз (раздел 4) |
| select, search, head, rename, fill, replace, slice | Один запрос, если у шагов есть SQL-форма | Построчно | `--where` для форматов, которые DuckDB не читает, считается пачками по 10 тыс. строк: Arrow → DuckDB |
| frequency, uniq, sort, sample, join, count | Да | Да; `uniq` — O(n²) | Результаты DuckDB возвращаются через `fetchall`/`fetchmany` в словари |
| dedup, reverse | Нет: `--engine` принимается, но игнорируется (`deduplicator.py:47`) | Да | `performance.md:35` обещает pushdown для `dedup` |
| stats | SUMMARIZE, затем 4 фазы запросов по каждому полю и выборка 10 тыс. строк для типов | Да | Типы в обоих путях определяет qddate |
| analyze, schema | DESCRIBE/SUMMARIZE | Выборка 10 тыс. объектов → pandas → DuckDB | pandas импортируется на уровне модуля |
| quality, schema-drift | Да; форматы, которые DuckDB не читает, идут через Arrow, а `quality` грузит их целиком в память | Правила проверяются вторым проходом | |
| validate, diff, split, mask, transpose, explode, enum | Нет | Да | `diff` держит в памяти ключи обоих файлов |
| sql | Представления над файлами | Вывод построчно через orjson | |
| db load | Только подсчёт строк | Пачками; для DuckDB — `executemany` | |

### 3.3 Структурные проблемы

- **Типы данных выводятся минимум в семи местах, и каждый раз по-своему:**
  - `ops/expr.py:111-150` — SQL, порог 95%;
  - `utils.TypeGuesser` — qddate;
  - `statistics/duckdb_engine.py:113-124`;
  - `ingester/duckdb_backend.py:79-135`;
  - `drift.py:147`;
  - `quality.py:241`;
  - `scheme.get_schema` в SDK против `duckdb_decompose` в CLI.

  В итоге `schema`, `stats`, `quality` и `schema-drift` могут давать разные типы для одного и того же файла.
- **Логика операций реализована дважды:**
  - команды `sorter`, `sampler`, `joiner`, `masker` и операции `ops` `Sort`, `Sample`, `Join`, `Mask`;
  - `uniq`/`frequency` в SDK и в `selector`;
  - `Dataset._sql_query` и `ops.runner.compose_sql`.
- **Построители SQL-выражений чтения продублированы, часть — без экранирования пути:** `selector.py:183,301`, `sampler.py:97`, `joiner.py:126`, `converter.py:665`. Ключи соединения в `joiner.py:140` не заключены в кавычки. Рядом при этом есть общий `duckdb_read_expr` (`command_utils.py:146`).
- **Настройки DuckDB применяются не везде.** В stats, count, analyze, schema, drift, quality и `Where` используется глобальный `duckdb.sql()`/`duckdb.connect()` без лимита памяти и temp-каталога. Ops-runner, наоборот, по умолчанию ставит `threads=1` и 256 МБ (`ops/runner.py:176`). Это сознательное решение ради сохранения порядка и памяти, но оно ограничивает скорость агрегатов.
- **Результаты DuckDB проходят через Python-словари:** `fetchmany(10k)` → `dict(zip)` → `normalize_for_json` (дважды). `COPY TO` используется только для CSV/Parquet без временных столбцов; JSON всегда пишется через Python.
- **SDK почти не использует DuckDB:**
  - в SQL компилируется только `write()`;
  - итерация, `count`, `head`, `uniq`, `frequency`, `validate` и `schema` всегда идут через Python, даже на CSV/Parquet;
  - `stats` и `quality` сначала материализуют план во временный JSONL;
  - `to_polars()` строит список словарей, а не передаёт Arrow.
- **Импорты тянутся и на DuckDB-пути.** `frequency` импортирует iterabledata (0,33 с) через `common/s3_iterable.py`. Это расходится с `performance.md`, где сказано, что DuckDB-команды iterabledata не импортируют.
- **Сообщения об ошибках разбора CSV рассчитаны на Python API, а не на CLI.** Они советуют `open_iterable('file.csv', iterableargs={...})` вместо флагов `--encoding`, `--delimiter`, `--on-error`.
- **Polars ранее уже был отклонён** в `openspec/changes/refactor-streaming-operations-core/design.md:35` как «новая тяжёлая зависимость, потоковый API ещё меняется».

**Стенд:** macOS arm64, 14 ядер, 36 ГБ ОЗУ, Python 3.13.

**Версии:** undatum 1.9.1 (PyPI), DuckDB 1.5.6 (Python-пакет, внутри undatum) и DuckDB CLI 1.5.4, Polars 2.1.0 (ленивый `scan_csv` + `sink_*`), pyarrow 26.0.0, pandas 3.1.0.

### 4.3 Почему `stats` занимает ~100 с

Время почти не зависит от размера файла: 106 с на 20 тыс. строк, 106 с на 40 тыс., 109 с на 2 млн.

Профиль показывает, что 98% времени уходит в `qddate.DateParser.match` → pyparsing. Вызов идёт из `utils.guess_datatype` (`undatum/utils.py:322`) через `TypeGuesser`.

Стоимость одного вызова qddate (`engine-review-2026-10-28/qdt.py`, одинаково на pyparsing 3.2.5 и 3.3.3):

| Значение | мс |
|---|---|
| `2020-01-02` (дата) | 0,23 |
| `city_3146` | 1,2 |
| `user105666@example.org` | 4,0 |
| `ul. Lenina 15, kv. 3` | 33 |
| `Lorem ipsum 90, "dolor" sit amet` | 44 |
| `c4ca4238a0b923820dcc509a6f75849b` (md5) | 55 |

`TypeGuesser` (`utils.py:384`, `date_probe=1000`) проверяет до 1000 значений на поле, прежде чем отказаться от поиска дат. Для столбца хэшей или адресов это 1000 × ~50 мс ≈ 50 с. Docstring класса оценивает стоимость в «до 0,5 мс на значение» — реальная стоимость на два порядка выше. Бюджет `stats` в CI (10,4 с на 1 млн строк) этого не ловит: в тестовых данных нет таких столбцов. На реальных открытых данных (адреса, ИНН с текстом, описания, хэши) это норма.

### 4.4 «Грязные» CSV

| Файл | undatum 1.9.1 | DuckDB (по умолчанию) | Polars (по умолчанию) |
|---|---|---|---|
| cp1251, разделитель `;`, ИНН с ведущими нулями | `sniff` распознаёт Windows-1251, `count` = 3000. Но `head` (auto → DuckDB) выводит **0 строк с кодом 0**, а `convert` падает с ошибкой UTF-8. С `--encoding cp1251` или `--engine python` всё работает | `CSV Error on Line: 2` | `invalid utf-8 sequence` |
| UTF-8, `н/д` в числовом столбце в строке 2500 | Работает, исходный текст сохранён | Работает: столбец VARCHAR, ведущие нули сохранены | `could not parse "н/д" as dtype i64` |
| Лишнее поле в строке 1500, разделитель `;` | Работает, но лишнее значение молча отбрасывается | Файл прочитан как один столбец: sniffer не определил `;` | Один столбец (по умолчанию `,`) |

Причина тихой потери данных — `duckdb_read_csv_options(..., ignore_errors=True)` по умолчанию (`common/command_utils.py:112-115`), плюс кодировка, определённая `sniff`, не передаётся в DuckDB. Под удар попадают все команды DuckDB-пути: head, select, search, rename, fill, replace, slice, sort, `--where`. Аналогичный `ignore_errors=true` для JSON есть в `statistics/duckdb_engine.py:151,239,496,625`.

## 5. Оценка движков

### 5.1 DuckDB — усиливать

**Состояние на 28.10.2026.**

- DuckDB 2.0.0 LTS вышел 21.10.2026 и поддерживается до октября 2027. Ветка 1.5 поддерживается до 01.03.2027, 1.4 LTS — до 17.11.2026 ([календарь](https://duckdb.org/release_calendar), [анонс 2.0](https://duckdb.org/2026/10/21/announcing-duckdb-200)).
- DuckDB 2.0, pandas 3.1, pyarrow 26 и Polars 2.x требуют Python ≥3.11 (проверено по PyPI). На Python 3.10 pip молча ставит старые ветки.
- Текущие ограничения undatum (`requires-python >=3.10`, `duckdb>=1.3,<2`) фиксируют проект на ветке 1.5.

**Что DuckDB даёт undatum:**

- **Самый устойчивый ридер CSV** — первое место в Pollock benchmark, 99,61% файлов прочитаны верно ([источник](https://duckdb.org/2025/04/16/duckdb-csv-pollock-benchmark)).
  - Опции `all_varchar`, `store_rejects` и таблица `reject_errors`: строка, позиция, столбец, тип ошибки и исходный текст строки.
  - Для не-UTF-8 — расширение `encodings` ([документация](https://duckdb.org/docs/2.0/data/csv/reading_faulty_csv_files.html)).
- **Форматы:** JSON/NDJSON, Parquet, Excel (`read_xlsx`/`COPY TO xlsx`), Avro (только чтение), Iceberg, Delta, DuckLake, spatial (GDAL), Vortex, Lance, httpfs/S3/GCS/Azure.
- **Операции:** `SUMMARIZE`, `approx_count_distinct`, `approx_quantile`, `USING SAMPLE reservoir/bernoulli ... REPEATABLE`, `QUALIFY`, `DISTINCT ON`. Сортировка, соединение, агрегация и оконные функции сбрасываются на диск.
- **Zero-copy сканирование Arrow-таблиц и потоков** — мост к iterabledata.

**Ограничения и риски:**

- Нет XML и BSON. В Excel: нет `.xls`, лимит 1 048 576 строк, типы выводятся по первой строке.
- Расширения (excel, httpfs, spatial, avro, encodings) скачиваются при первом использовании. Для закрытых контуров нужны `extension_directory` или предзагрузка.
- `string_agg` и упорядоченные агрегаты на диск не сбрасываются. Большие экспорты без `preserve_insertion_order=false` упираются в память.
- Python-UDF выполняются построчно под GIL; векторные Arrow-UDF работают быстро.
- Sniffer может ошибиться на «рваном» файле (раздел 4.4). Явный `delim`, как его передаёт undatum после собственного `sniff`, это решает.
- **Ломающие изменения Python API в 2.0** ([миграция](https://duckdb.org/docs/2.0/clients/python/migration)):
  - `fetch_record_batch`, `fetch_arrow_table`, `arrow()` и `pl()` у результатов `execute()` удалены; нужно `con.sql(q).to_arrow_reader(batch_size)`;
  - размер Arrow-батча по умолчанию уменьшен до 131 072;
  - общее соединение из нескольких потоков вызывает `ResourceInUseException`;
  - `write_csv(overwrite=False)` падает, если файл существует.

  В undatum затронут как минимум `common/repack_duckdb.py:209-215`. Web, MCP и Data API нужно проверить на разделяемые соединения.

**Вердикт:** DuckDB уже в зависимостях, лидирует по устойчивости к CSV и по операциям над множествами, а SQL-семантика `--where`/`--add` уже построена на нём. Правильный шаг — сделать его единым движком (раздел 5.4).

### 5.2 Polars — не как ядро, а как опция SDK

**Плюсы:**

- Скорость на уровне DuckDB.
- Выразительный API выражений.
- В 2.0 потоковый движок включён по умолчанию, со сбросом на диск.
- `scan_*`/`sink_*` для CSV, NDJSON, Parquet и IPC.
- SQLContext.
- Чтение Excel через fastexcel/calamine.

**Минусы для undatum (с доказательствами):**

1. **Нет выигрыша в скорости.** В 4.1 Polars быстрее DuckDB только на `sort` (0,61 против 0,65 с), на остальных 8 операциях медленнее или наравне. Независимые сравнения 2026 года дают разброс 1–3× в обе стороны в зависимости от нагрузки. При ограничении памяти до ~6 ГБ только DuckDB прошёл все запросы ([Uvik](https://uvik.net/blog/polars-vs-pandas/), [codecentric](https://www.codecentric.de/en/knowledge-hub/blog/duckdb-vs-polars-performance-and-memory-with-massive-parquet-data)).
2. **Вес.** `polars-runtime-32` — 48–54 МБ wheel и 153 МБ в установленном виде. Для DuckDB — 15–24 МБ и 44 МБ. Для CPU без AVX и для более чем 2³² строк нужны отдельные runtime-пакеты.
3. **«Грязные» данные.** По умолчанию схема выводится по 100 строкам, и чтение падает на смене типа. `ignore_errors` отбрасывает строки без отчёта. Кодировки кроме UTF-8 не поддерживаются (раздел 4.4). Для undatum, где главный сценарий — открытые данные, это критично.
4. **Нестабильность API.** Мажорная версия выходит примерно раз в 6 месяцев ([политика версий](https://docs.pola.rs/development/versioning)). В потоковом режиме join и group_by не сохраняют порядок строк без `maintain_order=True`.
5. **Второй SQL-диалект.** Пришлось бы дублировать `--where`/`--add`, вывод типов и сохранение исходного текста — ровно та дублирующая логика, от которой проект и так страдает (раздел 3.3).

**Как использовать:**

- `Dataset.to_polars()` через Arrow (`pl.from_arrow(rel.to_arrow_table())`) вместо списка словарей.
- Приём `pl.DataFrame`/`LazyFrame` как источника SDK через Arrow.
- Ограничение `polars>=1,<3` в extra оставить.
- Вернуться к вопросу, только если DuckDB перестанет покрывать какую-то операцию.

### 5.4 Целевая архитектура: «DuckDB-first, Arrow-native»

```text
источник ─┬─ читается DuckDB (CSV/TSV/JSON/JSONL/Parquet, xlsx и др. через расширения) ──► DuckDB relation
          └─ иначе: iterabledata ──► Arrow RecordBatchReader ──► DuckDB (zero-copy scan)

DuckDB relation ──► операции (SQL) ──┬─ COPY TO (CSV / Parquet / JSON[L] / xlsx)
                                     ├─ Arrow ──► writer iterabledata (прочие форматы)
                                     └─ Arrow ──► stdout в формате входа

Построчный Python остаётся для: правил валидации без SQL-формы, mask/AI,
форматов без Arrow-адаптера и явного --engine python.
```

Сохранение исходного текста CSV не меняется: `all_varchar` плюс типизированные теневые столбцы, как уже сделано в `ops/expr.py`.

### 6.2 Основные конкуренты: плюсы и минусы

- **qsv** — самый близкий конкурент по охвату, и он активно смещается к агентам: MCP, `describegpt`, HTML «Data Schematics», CKAN.
  - Плюсы — скорость Rust: индекс 15 ГБ / 28 млн строк за 14 с, `validate` до 1,34 млн строк/с, `diff` двух файлов по 1 млн строк менее чем за 0,6 с (данные из README qsv). Ещё плюсы — кэш статистики, переиспользуемый другими командами, и раздельные сборки бинаря.
  - Минусы — мажорная версия каждые 2–4 недели с ломающими изменениями, 80 команд без навигации, CSV-центричность (Parquet и Avro только через Polars-фичу, XML и BSON нет), бинарники для x86 требуют AVX2.
  - Главный соперник undatum в нише открытых данных и агентов.
- **DuckDB CLI** — стандарт для SQL по файлам: лучший ридер CSV, старт около 15 мс, экосистема расширений, режим сервера в 2.0. Минусы — только SQL, нет слоя валидации, качества и дрейфа, узкий набор форматов вне CSV/Parquet/JSON/Excel. undatum уже встраивает DuckDB, поэтому позиционироваться стоит как слой над ним, а не как замена.
- **Miller** — зрелый одиночный бинарь под BSD с отличным DSL, цепочками `then` и документацией, где каждый пример исполняется. Минусы — нет колоночных форматов, SQL и коннекторов к БД.
- **xan** — вероятно, самый быстрый CSV-инструмент вместе с zsv (по бенчмарку zsv). Есть визуализация в терминале и собственный язык выражений. Минусы — только CSV в UTF-8, строг к корректности строк, нет MCP и SDK.
- **csvkit** — Python-инструмент, который знают почти все. Минусы — медленный (qsv заявляет разрыв около 10 раз, н/п), держит данные в памяти, нет Parquet, проверок качества и MCP, редкие релизы. Это естественный источник пользователей для undatum: нужны эквиваленты команд и гайд по миграции.
- **sq** — аккуратный Go-бинарь с jq-подобными запросами, соединениями файл ↔ БД, `inspect` и `diff`. Пересекается с `db load`/`db dump` и `diff` в undatum. Минусы — меньше форматов, нет проверок качества.
- **frictionless-py** — стандарт Data Package и отчётов валидации, активно выпускается. Минусы — медленный, тяжёлый API, мало удобств в CLI, небольшое сообщество. undatum может стать быстрым Frictionless-совместимым CLI.
- **datacontract-cli и Soda Core** — туда в 2026 году уходят бюджеты на качество данных (контракты ODCS, контракты в Soda v4). Оба ориентированы на хранилища, а Soda перешла на ELv2. Правила и пороги undatum на уровне файлов можно сделать совместимыми с ODCS (чтение и запись), чтобы встроиться в эту экосистему.

### 6.3 Что учесть при разработке undatum

**Перенять:**

1. **Кэш и индексы рядом с данными** (как `qsv index` и кэш статистики, `.gzi` у xan). Каталог `.undatum/`, адресуемый хэшем файла, со статистикой, схемой и смещениями строк ускорит повторные запуски и вызовы агентов.
2. **Машиночитаемое самоописание.** По аналогии с `--export-tool-definitions` в qsv генерировать JSON-описания инструментов и манифест из Typer, рядом с уже версионированными схемами результатов.
3. **Публичные воспроизводимые бенчмарки** против csvkit, Miller, qsv, xan и DuckDB CLI на открытых наборах, включая Pollock для «грязных» CSV. Цель — показать, что DuckDB-пути конкурентны, а широта форматов — дополнительная ценность.
4. **Работа с «грязными» CSV:**
   - пропуск преамбулы и заголовочных строк;
   - `fixlengths` (уже есть);
   - файл отклонённых строк с отчётом — на базе `store_rejects`, а не `ignore_errors`.
5. **Визуализация в терминале и HTML-профиль** (`hist`/`plot` в xan, «Data Schematics» в qsv, HTML-отчёт ydata-profiling). У undatum есть `plot` и HTML у `quality` — их стоит объединить в один профиль.
6. **Документация:**
   - шпаргалки в духе Miller и xan;
   - страницы соответствия команд csvkit → undatum и qsv → undatum;
   - исполняемые примеры (уже есть `run_doc_examples.py`).
7. **Дистрибуция:**
   - `uvx undatum`, Homebrew, conda-forge и Docker как основные каналы;
   - лёгкое ядро и тяжёлые extras (как `qsvlite`/`qsvdp`);
   - бюджет времени запуска в CI;
   - CI-тест `undatum --help` на базовых зависимостях.

**Ниши, которые undatum может занять:**

- **Широта форматов за пределами CSV:** XML, BSON, Avro, ORC, геоформаты, научные форматы, lakehouse. qsv и xan центрированы на CSV, у DuckDB нет XML и BSON.
- **Одна MIT-установка для обработки, валидации, дрейфа, Frictionless и CI-порогов.** Вендоры качества данных консолидируются или меняют лицензии: GX Cloud ушёл к FICO, Soda — на ELv2, ingestr — на FSL, data-diff заброшен. Стабильная MIT-лицензия становится аргументом.
- **Безопасные инструменты для агентов:** MCP только для чтения, песочница по `--root`, версионированный JSON и коды выхода. При добавлении записи — явное разделение read- и write-инструментов, как `query`/`query_rw` у MotherDuck.
- **Python SDK** — его нет ни у одного из быстрых CLI-инструментов.
- **Сценарии порталов открытых данных** (Dateno, CKAN, Zenodo). qsv идёт сюда же с входами `ckan://` и выгрузкой в CKAN.

**Избегать:**

- Собственного SQL-движка для файлов: dsq, octosql, spyql, csvq и polars-cli заброшены.
- Частых ломающих релизов в стиле qsv: для пользователей в CI стабильный контракт CLI и semver важнее.
- Разрастания команд без навигации: группы команд и `undatum help <задача>`.
- GPL- и FSL-зависимостей в ядре.
- Гонки за скоростью разбора CSV против Rust/SIMD-инструментов. Конкурировать нужно широтой, корректностью, отчётами о качестве и удобством для агентов.

## 7. Рекомендации по приоритетам

### P0 — исправления в 1.9.x (корректность)

1. **Тихая потеря строк в DuckDB-пути.**
   - `ignore_errors` по умолчанию — `false`.
   - При `--on-error skip` использовать `store_rejects` и выводить число отклонённых строк в stderr и в JSON.
   - Передавать в DuckDB кодировку, определённую `sniff`. Если нужное расширение недоступно, переходить на Python-путь.
   - Тесты: cp1251, ведущие нули, рваные строки. Ключевые места: `common/command_utils.py:112-115`, `statistics/duckdb_engine.py`.
2. **`stats` и qddate.**
   - Дешёвый предфильтр: длина ≤ ~35 символов и форма даты (цифры и разделители); строки с буквами, кроме названий месяцев, отсекать.
   - `date_probe` уменьшить с 1000 до ~50–100; прекращать поиск после K промахов подряд.
   - Основное определение дат перенести в DuckDB (`TRY_CAST(... AS DATE/TIMESTAMP)`, `try_strptime` по выборке); qddate оставить для экзотических форматов на небольшой выборке.
   - Исправить docstring про «0,5 мс». Добавить в бюджеты CI данные с хэшами, адресами и свободным текстом.
3. **Python `uniq`:** `set` кортежей вместо списка (`cmds/selector.py:157`).
4. **`dedup` и `reverse`:** реализовать DuckDB-путь (`QUALIFY row_number() OVER (PARTITION BY ...) = 1`, `ORDER BY ... DESC` по номеру строки) или исправить `performance.md` и справку команд.
5. **Сообщения об ошибках разбора:** подсказывать CLI-флаги (`--encoding`, `--delimiter`, `--on-error skip`), а не `open_iterable(...)`.

### P1 — следующий минорный или мажорный релиз (движок)

6. **Платформа:** Python ≥3.11 (3.10 — EOL), `duckdb>=2.0,<3`. Исправить вызовы Arrow API, разделяемые соединения и семантику `overwrite`; прогнать матрицу CI.
7. **`convert` через `COPY` по умолчанию** для пар форматов, которые DuckDB читает и пишет (CSV/TSV/JSON/JSONL/Parquet). Контрактные тесты на сохранение текста (`all_varchar`) и дат: ускорение CSV→JSONL около 10 раз.
8. **Единая фабрика соединений** (`duckdb_config`) во всех командах:
   - `threads` по числу ядер для агрегатов и сортировки;
   - один поток для потоковых преобразований, где важен порядок;
   - `--memory-limit` и `--temp-dir` везде.
9. **`stats` за один-два прохода** вместо 4 × N запросов: один запрос с агрегатами по всем столбцам (count, nulls, min/max, `approx_count_distinct`, длины) и top-k через `GROUP BY`. Без `fetchall` словарей.
10. **Один модуль вывода типов на DuckDB** для `schema`, `stats`, `quality`, `schema-drift` и `db load`.
11. **Arrow-мост iterabledata → DuckDB** для форматов, которые DuckDB не читает. После этого удалить Python-дубли `sort`/`dedup`/`join`/`frequency` и оставить один SQL-путь.
12. **Вывод без Python-словарей:** `COPY TO` для файлов; Arrow → writer iterabledata для прочих форматов и stdout.

### P2 — развитие

13. **Офлайн-расширения DuckDB:** команда для предзагрузки excel, httpfs, spatial и encodings; включить их в Docker-образ и PyInstaller-сборки; настройка `extension_directory`.
14. **Excel:** чтение через fastexcel в Arrow (xls/xlsx/xlsb/ods), запись — DuckDB или текущие writers.
15. **SDK:**

16. **Валидация:**

## 8. Методика и ограничения

- **Замеры.**
  - Один прогон на одной машине (macOS arm64), «тёплый» кэш, время с запуском процесса. Скрипты в `engine-review-2026-10-28/`: `gen.py` (данные), `run.py` (прогон), `messy.py` и `probe.py` («грязные» CSV), `qdt.py` (qddate). Сырые результаты — `res_*.json`.
  - DuckDB CLI (1.5.4) запускается без Python; Polars — через Python-скрипт, поэтому его время включает ~0,25 с на запуск и импорт.
  - `stats` у инструментов не эквивалентен: undatum считает больше (типы, длины, словари). Но 98% его времени уходит на определение дат, а не на агрегаты.
- **Код.** Адреса строк указаны для коммита `a472331`. Выводы о путях исполнения получены чтением кода и проверены на выборочных местах (`ops/runner.py:176`, `cmds/selector.py:157`, `common/command_utils.py:112-115`, `cmds/deduplicator.py:47`).
- **Внешние данные** (версии, звёзды, даты, лицензии) собраны 28.10.2026 через GitHub API и PyPI. Версии DuckDB 2.0.0, Polars 2.1.0, pandas 3.1.0 и pyarrow 26.0.0 и их требование Python ≥3.11 проверены по PyPI.
- **Не подтверждено:**
  - числа db-benchmark;
  - точное число ломающих изменений Polars 2.0;
  - сброс hash join на диск в DataFusion;
  - поддержка ORC в DuckDB;
  - наличие MCP у datacontract-cli;
  - заявление qsv о «~10×» против csvkit;
  - цены Sling Platform.
